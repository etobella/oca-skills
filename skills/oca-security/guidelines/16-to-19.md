Rules for Odoo 16.0, 17.0, 18.0 and 19.0, on top of `generic.md`. A module of
one of these versions has `version` starting with `16.0.`, `17.0.`, `18.0.`
or `19.0.`.

# Access control in 16 to 19

Access is written in two places.

- **`security/ir.model.access.csv`** grants access to a model. Its columns
  are `id`, `name`, `model_id:id`, `group_id:id`, `perm_read`, `perm_write`,
  `perm_create` and `perm_unlink`. The rows of the groups a user belongs to
  add up.
- **Record rules (`ir.rule`)**, in XML, limit which records the grant
  reaches, with `domain_force`, the `groups` they apply to, and one flag per
  operation: `perm_read`, `perm_write`, `perm_create`, `perm_unlink`. A rule
  applies only to the operations whose flag is on. The rules of the user's
  groups add up (a record is allowed if any of them matches). A **global**
  rule, one with no groups, applies on top to every user, and all the global
  rules must match.

What to flag:

- **A row with no group.** An empty `group_id:id` grants to every user,
  portal and public ones included. Flag any such row that allows write,
  create or delete, and look at read on a model with sensitive data.
- **Rows for the open groups.** The same for rows that name the portal or
  the public group.
- **A global rule that covers some operations only.** A global rule with
  `perm_read` on and `perm_write` off does not stop a write. If a group's
  grant allows `write`, an attacker can change records that the read rule
  hides. Cover every operation that needs restricting.
- **A sensitive model with only group rules.** Group rules add up, so a user
  who matches one rule is allowed. A real restriction needs a global rule.
- **A multi-company model with no global company rule**, such as
  `['|', ('company_id', '=', False), ('company_id', 'in', company_ids)]`.
- **An `ir.access.csv` file** is from 20.0 and later. In a module of this
  range it is a mistake in a port: the rows it holds are not the rules of
  this version.

# Where to check create values in 16 to 19

`_prepare_create_values` belongs to newer versions. In these versions find,
in the source of the version, where `BaseModel.create` adds the missing
default values (look for `_add_missing_default_values`), and put the check on
the values after that step. Never check `vals` only, as
[Create overrides that check vals](generic.md#create-overrides-that-check-vals)
says. If you cannot find the step, say so.

# Constructs in 16 to 19

The versions of this range differ from each other. Before you recommend a
construct, check that the source of the module's version has it (search it
with `grep`), and use the fallback otherwise. If you cannot look, say you
did not check.

| Construct | In this range |
| --- | --- |
| Route `type` for JSON | `'json'` in 16.0 to 18.0. In 19.0 the name is `'jsonrpc'`, and `'json'` is a deprecated alias. |
| Combining domains | Do not assume `fields.Domain`. Use `odoo.osv.expression.AND` and `OR`, unless the version has `fields.Domain`. |
| Building SQL | Do not assume `odoo.tools.SQL` or `SQL.identifier`. Pass parameters to `cr.execute`, unless the version has them. |
| Hiding a field from everyone | Do not assume `fields.NO_ACCESS`. The fallback is `groups="base.group_system"`, which administrators can still read. |
| A public method that must not be called by RPC | Do not assume `@api.private`. Rename the method with a `_`, updating its callers. |
| x2many commands under `sudo()` | Do not assume `_allow_sudo_commands`. Whitelist the command lists by hand. |
| `t-raw` | The server QWeb of the version may still accept it. Where it does, it prints raw HTML: every use is a finding unless the value is proven escaped. OWL templates do not support it. |
| Invalidating the cache in a test | Use the call the version has: `self.env.invalidate_all()`, or `invalidate_cache()` in an older version. |
